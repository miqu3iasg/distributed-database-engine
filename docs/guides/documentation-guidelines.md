# Documentation Guidelines

Documentation is a first-class deliverable of GeoDB, not an afterthought: the project's value is _demonstrable, explained correctness_. Docs are written **incrementally**, in the same PR as the change they describe, and they are part of the Definition of Done.

## 1. Repository layout for documentation

```
docs/
├── adr/               Architecture Decision Records (one file per decision)
├── templates/         Templates, including adr-template.md
├── guides/            Contributor workflow guides (commits, PRs, docs, testing)
├── bugs/              Write-ups of bugs found ("bugs I found"), one file each
├── overview/          High-level description and the technical specification
└── EVIDENCE.md        Generated by CI. Do not edit by hand.
specs/tla/             TLA+ specifications
.github/               PR template, issue templates
AGENTS.md, CLAUDE.md   Agent guidance (repo root)
README.md              Entry point: architecture, guarantees, honest limitations, reproducible results
```

The **ADR template** lives at **`docs/templates/adr-template.md`**. Copy it to `docs/adr/` when starting a new ADR.

## 2. Document types and where they belong

| Type                    | Location             | Language | Mutability                                       |
| ----------------------- | -------------------- | -------- | ------------------------------------------------ |
| ADR                     | `docs/adr/`          | en-US    | Immutable once accepted (see section 5)          |
| Technical specification | `docs/overview/`     | pt-BR    | Living document, versioned                       |
| General description     | `docs/overview/`     | pt-BR    | Living document                                  |
| Guides (this folder)    | `docs/guides/`       | en-US    | Living                                           |
| Bug write-ups           | `docs/bugs/`         | en-US    | Append-only history                              |
| Evidence ledger         | `docs/EVIDENCE.md`   | en-US    | Generated by CI                                  |
| TLA+ specs              | `specs/tla/`         | n/a      | Versioned with code; mismatch with code is a bug |
| Code documentation      | Javadoc and comments | en-US    | Updated with the code                            |

If a document of the other language exists for the same topic, keep them consistent; the **ADR wins** over the spec, and the spec wins over the general description.

## 3. Front matter

Every markdown document under `docs/` starts with YAML front matter compatible with the Obsidian workflow already in use:

```yaml
---
title: <human title>
tags:
    - <type> # architecture, adr, documentation, guide, bug, ...
project: GeoDB
repository: geodb
path: docs/<folder>/<file>.md
lang: en-US # or pt-BR
date: "YYYY-MM-DD"
id: <uuid> # stable identifier
---
```

ADRs add the optional relationship fields `supersedes` and `superseded_by` (see below). Cross-reference related documents with Obsidian wikilinks (`[[doc-name]]`) in a final References section, and with normal relative links where the repo is browsed on GitHub.

## 4. Architecture Decision Records (ADRs)

### 4.1 When to write an ADR

Write an ADR when a decision:

- is hard or expensive to reverse (language, storage format, wire protocol, consistency model);
- has real alternatives that were considered and rejected;
- constrains other modules (for example the determinism rules);
- changes a correctness assumption (clock-offset bound, isolation level, read path);
- will make a future reader ask "why on earth did they do it this way?"

Also write ADRs for **what you chose not to do** (for example merge of ranges) when it is a deliberate trade-off.

Do **not** write an ADR for routine implementation choices, naming, or anything fully visible and cheaply reversible in code.

### 4.2 Structure (follow `docs/templates/adr-template.md`)

1. **Context**: the forces at play, the problem, the constraints, and why a decision is needed now.
2. **Decision**: what we do, stated in active voice and precisely enough to be checked against the code (numbers, formats, rules).
3. **Alternatives Considered**: each real alternative, with the reason it was rejected. Alternatives must be genuinely plausible, not strawmen.
4. **Consequences**: split into **Positive** and **Negative**. The negatives must be honest; an ADR with no downsides is not credible.
5. **References**: papers, reference implementations, and `[[wikilinks]]` to related ADRs.

### 4.3 Naming and numbering

- File: `docs/adr/adr-NNNN-<kebab-slug>.md`, with a **four-digit** sequential number (`adr-0014-...`).
- Heading: `# ADR-NNNN <Title>`; cross-references in text use the same four digits (`ADR-0004`).
- The `path` front-matter field must match the file's real path.
- Numbers are never reused, even for rejected or superseded ADRs.

### 4.4 Lifecycle and status

States: **Proposed** → **Accepted** → (**Deprecated** | **Superseded**). Rejected proposals are kept, marked as such, with the reasoning.

- Add a `status` field to the front matter (`proposed`, `accepted`, `deprecated`, `superseded`). Existing ADRs should be backfilled as `accepted`.
- An accepted ADR is **not rewritten**. Typos and broken links may be fixed. To change a decision, write a **new ADR** that links `supersedes: "[[old-adr]]"`, and set `superseded_by: "[[new-adr]]"` and `status: superseded` on the old one.
- An ADR is written **before or together with** the code that implements it, in the same PR or an earlier one. Never retroactively invent the rationale months later.

### 4.5 Writing style

- Short, concrete, and checkable. Prefer numbers and formats over adjectives.
- State the trade-off explicitly ("we accept X to get Y").
- Cite sources: papers, thesis chapters, reference code. Link them.
- One decision per ADR. If you are tempted to write "and also", split it.

## 5. The technical specification and overview

- The spec defines _what will be built, with which structures, and why_. Items marked **[ADR]** must have a corresponding ADR before the related feature is implemented.
- When code and spec diverge, the divergence is a bug in one of them. Fix it in the same PR and say which side was wrong.
- Bump the spec `version` in front matter on meaningful changes and keep the status line consistent.
- If a change makes `AGENTS.md`, `CLAUDE.md`, or a guide stale, update it in the same PR.

## 6. Bug write-ups (`docs/bugs/`)

Every bug found by simulation, checkers, fuzzing, chaos, or review gets a short write-up: `docs/bugs/NNNN-<slug>.md` containing:

- **Summary** and **severity** (data loss, safety violation, liveness, performance, minor).
- **How it was found**: layer (simulation, lincheck, Elle, fuzz, chaos, review) and the **seed** or input.
- **Root cause** and the invariant or property that was violated.
- **Fix** (commit/PR) and the **regression** (test or corpus entry).
- **Lesson**: what this teaches, and whether a new invariant, ADR, or nemesis fault is warranted.

These feed `docs/EVIDENCE.md` categories and the project's "bugs I found" write-up.

## 7. Evidence ledger

`docs/EVIDENCE.md` is **generated by CI** (seeds executed, simulated hours, bugs by category, validated history sizes, mutation score, benchmark results, TLC states explored). Never hand-edit it, and never paste numbers into prose that are not backed by it. Methodology and limitations accompany every benchmark figure.

## 8. Code-level documentation

- **Javadoc** on every public type and method of module APIs, stating contracts, thread-safety, determinism requirements, and failure behavior. Document _invariants_ and _ordering requirements_ (for example the `Ready`/`advance` contract) where they live.
- **Comments explain why**, not what. Link to the ADR or spec section for non-obvious decisions.
- Raft handlers reference the formal spec: `/* TLA: HandleAppendEntriesRequest */`.
- Persisted formats (WAL record, SSTable block, MANIFEST edit, MVCC key) are documented next to the codec **and** in the spec, with a test that pins the byte layout.

## 9. Diagrams

- Use **Mermaid** blocks or ASCII diagrams so they live in version control and render on GitHub. Avoid binary image formats unless unavoidable.
- A diagram supports the text; it does not replace the explanation of invariants.

## 10. Review and quality checks

A documentation change is reviewed like code. Check:

- Is it accurate against the current code and ADRs?
- Are alternatives real and the negatives honest?
- Are front matter, numbering, and `path` correct? Do links resolve?
- Are claims backed by evidence, or clearly marked as hypotheses?
- Is the language correct for the document type (en-US for ADRs and guides; pt-BR for spec and overview)?

CI should (planned) run a link checker and a front-matter validator over `docs/`.

## 11. For AI agents

When documenting, agents follow the templates exactly, preserve front matter and wikilinks, never rewrite an accepted ADR (they propose a superseding one), report contradictions between documents instead of silently choosing, and never state measured results they did not obtain from a real run.
